Unit Testing (Tools: PyTest)

Setelah mengenal JUnit pada Java, sesi ini membawa konsep unit testing yang sama ke Python lewat PyTest: sintaks lebih ringkas, fixture yang fleksibel, dan ekosistem plugin yang luas. Konsepnya tidak berubah — yang berbeda hanya alat dan gaya penulisannya.

⏱ 50 menit 🎯 CPMK-3, CPMK-4 🐍 Python 3 + PyTest

Tujuan Pembelajaran

Setelah mengikuti sesi ini, mahasiswa mampu:

  • ✓ Membandingkan PyTest dengan JUnit dan unittest bawaan Python.
  • ✓ Menulis dan menjalankan test PyTest sesuai konvensi penamaan.
  • ✓ Menguji exception dengan pytest.raises.
  • ✓ Memakai fixture, parametrize, dan marker.
  • ✓ Menggunakan mocking dasar dan mengukur coverage dengan pytest-cov.
9.1

💡PyTest memakai pernyataan assert Python biasa, lalu menulis ulang (assertion rewriting) agar saat gagal ia menampilkan nilai kedua sisi secara rinci — tanpa perlu menghafal puluhan method assertion.
9.2

Test Pertama & Konvensi

Instalasi: pip install pytest pytest-cov. Contoh kode yang diuji (setara DiscountCalculator di sesi 8):

# discount.py def apply_discount(total): if total < 0: raise ValueError("Total negatif") if total >= 500_000: return total * 0.90 # diskon 10% return total
# test_discount.py from discount import apply_discount def test_diskon_di_batas_atas(): assert apply_discount(500_000) == 450_000 def test_tanpa_diskon_di_bawah_batas(): assert apply_discount(499_999) == 499_999

Jalankan dengan pytest -v. PyTest menemukan test secara otomatis berdasarkan konvensi:

  • 01
    Nama file
    test_*.py atau *_test.py
  • 02
    Nama fungsi
    Diawali test_
  • 03
    Nama class
    Diawali Test dan tanpa method __init__
⚠Jebakan umum: file bernama discount_test_1.py atau fungsi bernama cek_diskon() tidak akan dijalankan — dan PyTest tidak memberi peringatan. Selalu cek jumlah test yang terdeteksi pada ringkasan hasil.
9.3

Assertion & Pengujian Exception

import pytest def test_total_negatif_ditolak(): with pytest.raises(ValueError, match="Total negatif"): apply_discount(-1) def test_float_dengan_toleransi(): assert apply_discount(500_001) == pytest.approx(450_000.9)

pytest.approx menghindari kegagalan semu akibat ketidakpresisian bilangan pecahan, sama fungsinya dengan parameter delta pada assertEquals di JUnit.

9.4

Fixture

Fixture adalah fungsi penyedia kondisi awal (data, objek, koneksi) yang disuntikkan ke test lewat nama parameter. Menggantikan @BeforeEach/@AfterEach dengan cara yang lebih fleksibel.

import pytest @pytest.fixture def keranjang(): k = Keranjang() # Arrange k.tambah("Buku", 50_000) yield k # diberikan ke test k.kosongkan() # cleanup setelah test selesai def test_total_keranjang(keranjang): assert keranjang.total() == 50_000
ScopeFixture dibuat ulang…
function (default)untuk setiap test
modulesekali per file
sessionsekali untuk seluruh sesi pengujian
✓Fixture bersama diletakkan di conftest.py agar otomatis tersedia bagi semua file test dalam folder tersebut.
9.5

Parametrize & Marker

@pytest.mark.parametrize("total, diharapkan", [ (0, 0), (499_999, 499_999), # batas bawah (500_000, 450_000), # tepat di batas (1_000_000, 900_000), ]) def test_hitung_diskon(total, diharapkan): assert apply_discount(total) == diharapkan

Marker memberi label pada test sehingga dapat dipilih atau dilewati:

MarkerFungsi
@pytest.mark.skip(reason=...)Melewati test
@pytest.mark.xfailDiharapkan gagal (bug yang sudah diketahui)
@pytest.mark.slow (kustom)Dijalankan selektif: pytest -m "not slow"
9.6

Mocking

Mocking adalah teknik mengganti dependensi asli (database, API eksternal, layanan email, jam sistem) dengan objek pengganti yang dapat dikendalikan selama pengujian. Tujuannya agar yang diuji benar-benar logika unit itu sendiri, bukan perilaku sistem lain di sekitarnya.

Kegunaan Mocking

  • 01
    Isolasi
    Test gagal hanya jika kode yang diuji bermasalah, bukan karena internet mati atau database kosong.
  • 02
    Cepat & repeatable
    Tidak ada panggilan jaringan; hasil sama di laptop, CI, maupun komputer teman.
  • 03
    Menghindari efek samping nyata
    Tidak mengirim email sungguhan, tidak menagih kartu kredit, tidak menghapus data produksi.
  • 04
    Mensimulasikan kondisi sulit
    Timeout, error 500, atau respons aneh dari API mudah dipicu lewat mock, tetapi sulit dibuat dengan layanan asli.
  • 05
    Memverifikasi interaksi
    Memastikan fungsi tertentu dipanggil, berapa kali, dan dengan argumen apa.

Jenis Test Double

JenisPeranContoh
DummyPengisi parameter, tidak pernah dipakaiNone atau objek kosong
StubMengembalikan jawaban tetapAPI kurs selalu menjawab 15.000
FakeImplementasi sederhana yang sungguh berfungsiDatabase dalam memori (dict/SQLite)
MockStub yang juga merekam dan memverifikasi pemanggilanassert_called_once_with(...)
SpyMembungkus objek asli sambil merekam pemanggilannyapatch.object(..., wraps=...)

Contoh Lengkap

Kode yang diuji memanggil layanan email eksternal:

# app.py from email_service import kirim_email # dependensi eksternal def proses_pesanan(id, email): if id <= 0: raise ValueError("ID tidak valid") ok = kirim_email(email, f"Pesanan {id} diterima") return "selesai" if ok else "email gagal"
# test_app.py from unittest.mock import patch import pytest from app import proses_pesanan def test_pesanan_sukses_dan_email_terkirim(): with patch("app.kirim_email", return_value=True) as palsu: # stub + mock assert proses_pesanan(1, "a@b.id") == "selesai" palsu.assert_called_once_with("a@b.id", "Pesanan 1 diterima") def test_email_gagal_ditangani(): with patch("app.kirim_email", return_value=False): assert proses_pesanan(1, "a@b.id") == "email gagal" def test_layanan_email_timeout(): with patch("app.kirim_email", side_effect=TimeoutError): # simulasi error with pytest.raises(TimeoutError): proses_pesanan(1, "a@b.id") def test_id_tidak_valid_tidak_mengirim_email(): with patch("app.kirim_email") as palsu: with pytest.raises(ValueError): proses_pesanan(0, "a@b.id") palsu.assert_not_called() # verifikasi interaksi
⚠Jebakan paling umum: salah target patch. Patch harus menunjuk ke tempat nama itu dipakai ("app.kirim_email"), bukan tempat ia didefinisikan ("email_service.kirim_email"). Karena app.py sudah mengimpor nama tersebut, patch pada modul asal tidak berpengaruh dan email asli tetap terkirim.

Alternatif: monkeypatch & Fixture

def test_dengan_monkeypatch(monkeypatch): monkeypatch.setattr("app.kirim_email", lambda to, msg: True) assert proses_pesanan(1, "a@b.id") == "selesai" # Mengatur variabel lingkungan tanpa mengubah sistem asli def test_env(monkeypatch): monkeypatch.setenv("API_KEY", "palsu-123")

monkeypatch otomatis mengembalikan kondisi semula setelah test selesai. Ia cocok untuk penggantian sederhana; unittest.mock lebih cocok bila Anda perlu memverifikasi pemanggilan.

Kapan Tidak Perlu / Jangan Berlebihan

Mock ini

  • Jaringan, API pihak ketiga, email/SMS
  • Database dan sistem berkas (atau pakai fake)
  • Waktu (datetime.now) dan nilai acak

Jangan mock

  • Kode milik unit yang sedang diuji
  • Fungsi murni sederhana (cukup dipanggil langsung)
  • Semuanya sekaligus: test jadi hanya memeriksa mock itu sendiri
💡Mock hanya membuktikan unit bekerja jika asumsi kita tentang dependensi benar. Kontrak sebenarnya dengan layanan asli tetap perlu diverifikasi lewat integration test dan contract test, termasuk pada proyek lintas mata kuliah nanti.
9.7

Coverage

Code coverage adalah persentase kode sumber yang dieksekusi saat test berjalan. Di sesi 6 Anda mempelajari Statement dan Branch Coverage secara teori; pytest-cov (berbasis coverage.py) menghitungnya otomatis.

Kegunaan Coverage

  • ✓ Menemukan kode yang belum diuji — baris, fungsi, atau cabang yang tidak pernah dijalankan test.
  • ✓ Memandu penambahan test — laporan menunjuk nomor baris yang terlewat.
  • ✓ Menjaga standar tim — CI dapat menolak perubahan yang menurunkan coverage.
  • ✓ Bukti pengujian untuk laporan, termasuk bagian eksekusi pengujian di proyek.

Statement vs Branch Coverage

# fungsi dengan satu if tanpa else def bayar(total, member): if member: total *= 0.9 return total # Test: bayar(100, True) # Statement coverage = 100% (semua baris dijalankan) # Branch coverage = 50% (cabang member=False tak pernah diuji)

Itulah alasan flag --cov-branch disarankan: statement coverage saja dapat menyembunyikan cabang yang belum diuji.

Menjalankan & Membaca Laporan

pytest --cov=app --cov-branch --cov-report=term-missing --cov-report=html
Name Stmts Miss Branch BrPart Cover Missing ---------------------------------------------------- app.py 12 2 6 1 83% 18-19, 7->9 ---------------------------------------------------- TOTAL 12 2 6 1 83%
KolomArti
Stmts / MissJumlah statement / yang tidak dieksekusi
Branch / BrPartJumlah cabang / cabang yang hanya sebagian teruji
Missing18-19 = baris tak tersentuh; 7->9 = lompatan dari baris 7 ke 9 tak pernah terjadi

Opsi --cov-report=html membuat folder htmlcov/; buka index.html untuk melihat kode dengan baris merah (belum teruji) dan hijau (teruji). Untuk CI, tambahkan --cov-fail-under=80 agar build gagal bila coverage di bawah 80%.

Keterbatasan Coverage

def test_tanpa_assertion(): apply_discount(500_000) # dieksekusi, tetapi hasil tidak diperiksa # coverage naik, bug tetap lolos
⚠Coverage mengukur kode yang dijalankan, bukan kebenaran hasilnya. Angka 100% tidak berarti bebas bug, dan bug berupa fitur yang hilang (tidak ada kodenya) tidak akan terlihat sama sekali. Gunakan coverage sebagai alat untuk menemukan celah, bukan sebagai target tujuan akhir; target yang wajar umumnya 70–85% dengan branch coverage pada logika bisnis penting.

Latihan

Konversi Nilai Angka ke Huruf

Requirement: "Fungsi grade(nilai) mengembalikan A (≥85), B (70–84), C (55–69), D (40–54), E (<40). Nilai di luar 0–100 melempar ValueError."

  • Tentukan nilai uji dengan BVA pada setiap batas, termasuk 0, 100, -1, dan 101.
  • Tulis satu test parametrize dan satu test pytest.raises.
  • Ubah fungsi menjadi memakai dua fixture berbeda? Diskusikan: apakah di sini fixture diperlukan?

Jalankan dengan --cov-branch: cabang mana yang belum tersentuh oleh test Anda?

Rangkuman

  • ✓ PyTest menyederhanakan penulisan test: fungsi biasa dan assert Python native.
  • ✓ Test ditemukan otomatis berdasarkan konvensi penamaan file, fungsi, dan class.
  • ✓ Fixture mengelola setup/cleanup; parametrize menjalankan satu logika dengan banyak data hasil EP/BVA.
  • ✓ Mocking menjaga isolasi unit dari dependensi eksternal.
  • ✓ pytest-cov mengukur coverage, tetapi kualitas assertion tetap yang utama.

Latihan Pemahaman Mandiri

Klik tiap soal untuk melihat kunci jawaban.

1. Mengapa fungsi cek_diskon() di file test_discount.py tidak dijalankan PyTest?
Jawaban: Karena nama fungsi tidak diawali test_, sehingga tidak ikut ditemukan secara otomatis.
2. Apa keunggulan fixture dibanding menyalin kode setup di setiap test?
Jawaban: Kode setup ditulis sekali dan dipakai ulang lewat parameter, mendukung cleanup dengan yield, mengatur scope, dan dapat dibagi lewat conftest.py.
3. Kapan memakai xfail dan bukan skip?
Jawaban: xfail untuk test yang tetap dijalankan tetapi diharapkan gagal karena bug yang sudah diketahui; jika tiba-tiba lulus, PyTest melaporkannya. skip sama sekali tidak menjalankan test.
4. Mengapa panggilan ke API pembayaran eksternal sebaiknya di-mock pada unit test?
Jawaban: Agar test cepat, repeatable, tidak bergantung pada jaringan atau layanan pihak ketiga, dan tidak menimbulkan efek samping nyata seperti transaksi sungguhan.

Unit Test PyTest dengan Fixture dan Parametrize

Buat modul Python dengan minimal 3 fungsi berlogika bersyarat (boleh versi Python dari tugas sesi 8). Tulis test PyTest yang mencakup:

(1) Minimal 8 test, termasuk 1 parametrize berdasar BVA
(2) Minimal 2 test pytest.raises untuk skenario negatif
(3) Minimal 1 fixture (dengan cleanup memakai yield) dan 1 penggunaan mock
(4) Laporan pytest --cov --cov-branch beserta analisis singkat cabang yang belum tercakup
