Jenis-jenis Testing

Testing bukan aktivitas tunggal — ia terbagi dalam beberapa sumbu klasifikasi yang saling independen. Sesi ini membangun peta klasifikasi yang akan dipakai untuk memahami hampir seluruh materi setelahnya.

⏱ 50 menit 🎯 CPMK-1, CPMK-2 📖 3 referensi utama

Tujuan Pembelajaran

Setelah mengikuti sesi ini, mahasiswa mampu:

  • ✓ Membedakan Functional Testing dan Non-Functional Testing beserta contoh masing-masing.
  • ✓ Menjelaskan sub-jenis Non-Functional Testing (performance, usability, security, reliability, compatibility, safety) dan mengaitkannya dengan karakteristik ISO/IEC 25010:2023 dari Sesi 2.
  • ✓ Membedakan Manual Testing dan Automated Testing beserta kelebihan-kekurangannya.
  • ✓ Menjelaskan konsep Automation Testing Pyramid dan alasan di baliknya.
  • ✓ Mengklasifikasikan skenario testing nyata ke dalam kombinasi keempat sumbu (functional/non-functional × manual/otomatis).
3.1

Functional Testing vs Non-Functional Testing

Ini adalah sumbu klasifikasi paling mendasar dalam testing — membedakan apa yang dilakukan sistem dari seberapa baik sistem melakukannya.

Functional Testing

"Apakah fitur ini bekerja sesuai spesifikasi?"

Menguji apa yang dilakukan sistem — fitur, fungsi bisnis, alur kerja. Berbasis input-proses-output, biasanya diuji dengan pendekatan black-box.

  • Login berhasil dengan kredensial benar
  • Perhitungan total belanja sudah akurat
  • Validasi form menolak input tidak valid

Non-Functional Testing

"Seberapa baik sistem menjalankan fungsi tersebut?"

Menguji kualitas menjalankan fungsi — kecepatan, keamanan, kemudahan pakai, daya tahan. Berkaitan langsung dengan 8 karakteristik kualitas ISO/IEC 25010:2023 (Sesi 2) selain Functional Suitability.

  • Halaman termuat dalam <2 detik
  • Sistem tahan 1000 pengguna bersamaan
  • Data pengguna terenkripsi dengan aman
✓ Cara cepat membedakan: jika pertanyaannya "apakah fitur X ADA dan BEKERJA?" → functional. Jika pertanyaannya "apakah fitur X CUKUP CEPAT/AMAN/MUDAH DIPAKAI?" → non-functional.
3.2

Sub-jenis Non-Functional Testing

Non-Functional Testing bukan satu jenis tunggal — ia terbagi menjadi beberapa sub-jenis, masing-masing memetakan langsung ke karakteristik ISO/IEC 25010:2023 yang sudah dibahas di Sesi 2.

⚠ Catatan istilah: nama sub-jenis testing di industri (kolom kiri) sebagian besar tetap dipakai secara informal meski nama karakteristik resminya di ISO/IEC 25010:2023 sudah berubah — misalnya "Usability Testing" tetap lazim disebut demikian meski karakteristik ISO-nya kini bernama Interaction Capability.
Sub-jenis Testing Karakteristik ISO/IEC 25010:2023 Contoh Pertanyaan Uji
Performance Testing Performance Efficiency Berapa waktu respons di bawah beban tinggi? (dibahas mendalam di Sesi 13)
Usability Testing Interaction Capability (dahulu: Usability) Bisakah pengguna baru menyelesaikan tugas tanpa panduan?
Security Testing Security Apakah sistem tahan terhadap upaya akses tidak sah?
Reliability Testing Reliability Apakah sistem tetap stabil dijalankan terus-menerus selama 72 jam?
Compatibility Testing Compatibility Apakah tampilan tetap benar di berbagai browser/device?
Portability / Configuration Testing Flexibility (dahulu: Portability) Apakah sistem tetap berjalan baik saat dipindahkan ke lingkungan/server lain?
Safety Testing · baru Safety (karakteristik baru 2023) Apakah kegagalan sistem berpotensi mencederai pengguna atau merusak properti?
💡 Perhatikan bahwa tabel ini secara langsung menyambung ke model kualitas ISO/IEC 25010:2023 di Sesi 2 — non-functional testing pada dasarnya adalah cara mengukur apakah 8 karakteristik kualitas non-fungsional tersebut benar-benar terpenuhi.
3.3

Manual Testing vs Automated Testing

Sumbu klasifikasi kedua ini independen dari functional/non-functional — keduanya bisa diuji baik secara manual maupun otomatis. Perbedaannya terletak pada siapa/apa yang mengeksekusi test case.

Manual Testing

Tester menjalankan test case secara langsung, mengamati hasil dengan mata sendiri, dan membandingkannya dengan hasil yang diharapkan.

Kelebihan
  • Fleksibel untuk kasus eksploratif
  • Cocok untuk usability testing
  • Tidak perlu investasi tools/script
Kekurangan
  • Lambat & melelahkan untuk repetitif
  • Rawan human error
  • Sulit di-scale untuk regresi besar

Automated Testing

Test case dijalankan oleh script/tools (mis. Selenium, JUnit, Cypress) tanpa intervensi manual saat eksekusi.

Kelebihan
  • Cepat & konsisten untuk repetitif
  • Ideal untuk regression testing
  • Bisa dijalankan otomatis di CI/CD
Kekurangan
  • Butuh investasi waktu menulis script
  • Perlu maintenance saat UI berubah
  • Kurang cocok untuk exploratory/usability
⚠ Miskonsepsi umum: "automated testing selalu lebih baik dari manual testing". Faktanya keduanya saling melengkapi — automation unggul untuk regression testing berulang, sementara manual (khususnya exploratory testing) unggul untuk menemukan masalah usability atau skenario tak terduga yang script tidak pernah dirancang untuk mendeteksinya.
3.4

Automation Testing Pyramid

Ketika sebuah tim memutuskan mengotomasi testing-nya, muncul pertanyaan: pada level mana sebaiknya proporsi automation paling besar? Jawabannya digambarkan lewat Testing Pyramid.

E2E / UI Testingpaling lambat & rapuh — porsi paling sedikit
Integration Testingporsi menengah
Unit Testingpaling cepat & stabil — porsi paling besar

Semakin ke atas piramida, test semakin lambat dieksekusi, semakin rapuh (mudah gagal karena perubahan kecil pada UI), dan semakin mahal untuk dipelihara — sehingga porsinya harus semakin sedikit. Semakin ke bawah, test semakin cepat, stabil, dan murah untuk dijalankan berulang kali — sehingga sebaiknya menjadi porsi terbesar dari total automation suite.

✓ Konsep piramida ini akan dipakai kembali secara konkret di Sesi 9–10 (Unit Testing dengan JUnit/PyTest) dan Sesi 12 (Automated Testing dengan Selenium/Cypress) sebagai dasar strategi automation.
3.5

Matriks Klasifikasi: Menggabungkan Kedua Sumbu

Karena functional/non-functional dan manual/otomatis adalah dua sumbu yang independen, keduanya bisa dikombinasikan menjadi matriks 2×2 — setiap skenario testing nyata pasti masuk ke salah satu dari empat kuadran ini.

Manual
Otomatis
Functional
Tester mencoba fitur checkout secara langsung di aplikasi.
Contoh: exploratory testing fitur baru
Script otomatis menjalankan skenario login berulang kali.
Contoh: regression suite dengan Selenium
Non-Functional
Tester menilai kemudahan navigasi aplikasi bagi pengguna baru.
Contoh: usability testing dengan observasi langsung

Contoh: load testing dengan JMeter

📝 Diskusikan hasil klasifikasi Anda dengan pasangan, lalu bandingkan dengan kelas — asisten/dosen akan membahas jawaban dan alasan di akhir sesi.

Rangkuman

  • ✓ Functional Testing menguji apa yang dilakukan sistem; Non-Functional Testing menguji seberapa baik sistem melakukannya.
  • ✓ Non-Functional Testing terbagi menjadi performance, usability, security, reliability, compatibility, dan safety testing — masing-masing memetakan ke karakteristik ISO/IEC 25010:2023.
  • ✓ Manual Testing unggul untuk eksplorasi dan usability; Automated Testing unggul untuk regression testing yang repetitif.
  • ✓ Automation Testing Pyramid merekomendasikan porsi terbesar automation di level Unit Testing, bukan di level UI/E2E.
  • ✓ Functional/Non-Functional dan Manual/Otomatis adalah dua sumbu klasifikasi independen — setiap skenario testing nyata berada di salah satu dari empat kombinasi kuadran.

Latihan Pemahaman Mandiri

Klik tiap soal untuk melihat kunci jawaban dan penjelasannya.

1. Menguji apakah aplikasi tetap dapat digunakan setelah dijalankan non-stop selama 7 hari — termasuk sub-jenis non-functional testing apa?
Jawaban: Reliability Testing — mengukur kemampuan sistem menjalankan fungsinya secara konsisten dalam periode waktu tertentu tanpa gagal.
2. Mengapa exploratory testing sulit sepenuhnya digantikan oleh automated testing?
Jawaban: Karena automated testing hanya menjalankan skenario yang sudah didefinisikan sebelumnya dalam script, sementara exploratory testing mengandalkan intuisi dan kreativitas tester untuk menemukan skenario tak terduga yang belum pernah dipikirkan siapa pun sebelumnya.
3. Sebuah tim menghabiskan sebagian besar automation suite mereka pada UI/E2E testing, hanya sedikit unit test. Apa risiko dari strategi ini menurut Testing Pyramid?
Jawaban: Test suite akan lambat dieksekusi, rapuh (mudah gagal akibat perubahan kecil pada tampilan), dan mahal untuk dipelihara — bertentangan dengan rekomendasi piramida yang menempatkan porsi terbesar pada unit testing yang cepat dan stabil.
4. Skenario "memastikan data kartu kredit terenkripsi saat transmisi" termasuk kuadran mana pada matriks klasifikasi?
Jawaban: Non-Functional (Security Testing) dan biasanya diuji secara Otomatis menggunakan tools security scanning, meski sebagian pengujian keamanan mendalam (mis. penetration testing) tetap memerlukan komponen manual oleh ahli keamanan.
