Automated Testing (Selenium, Cypress, dsb.) & Pengenalan Integrasi CI/CD

Unit test mencakup level terkecil. Sesi ini naik ke pengujian otomatis pada level antarmuka (UI) dan API, lalu menghubungkan seluruh test ke pipeline CI/CD sehingga setiap perubahan kode diuji otomatis tanpa campur tangan manual.

⏱ 50 menit 🎯 CPMK-3, CPMK-4 ⚙ Otomasi & Pipeline

Tujuan Pembelajaran

Setelah mengikuti sesi ini, mahasiswa mampu:

  • ✓ Menentukan test yang layak dan tidak layak diotomasi.
  • ✓ Membandingkan Selenium, Cypress, dan tools sejenis.
  • ✓ Menulis skrip pengujian UI dasar dengan locator dan penantian yang tepat.
  • ✓ Menerapkan Page Object Model dan menghindari flaky test.
  • ✓ Menjelaskan konsep CI/CD dan menyusun pipeline sederhana yang menjalankan test otomatis.
11.1

Mengapa Otomasi Pengujian?

Test automation adalah penggunaan skrip dan tools untuk mengeksekusi test dan membandingkan hasil aktual dengan hasil yang diharapkan tanpa intervensi manual.

Layak diotomasi

  • Regression test yang berulang tiap rilis
  • Smoke test pada jalur kritis (login, checkout)
  • Test dengan banyak kombinasi data
  • Test lintas browser/perangkat

Kurang layak diotomasi

  • Fitur yang masih sering berubah
  • Exploratory testing dan penilaian kegunaan (usability)
  • Test yang hanya dijalankan sekali
  • Penilaian visual yang subjektif
💡Piramida otomasi: idealnya banyak unit test (sesi 9–10), lebih sedikit test API/integrasi, dan paling sedikit test UI end-to-end. Test UI paling lambat, paling rapuh, dan paling mahal dipelihara, jadi dipakai hanya untuk alur bisnis terpenting.

11.3

Selenium WebDriver

Contoh skenario login memakai Selenium 4 dengan PyTest (kelanjutan sesi 9):

import pytest from selenium import webdriver from selenium.webdriver.common.by import By from selenium.webdriver.support.ui import WebDriverWait from selenium.webdriver.support import expected_conditions as EC @pytest.fixture def driver(): opts = webdriver.ChromeOptions() opts.add_argument("--headless=new") # tanpa jendela, cocok untuk CI d = webdriver.Chrome(options=opts) yield d d.quit() # cleanup def test_login_berhasil(driver): driver.get("https://contoh.app/login") driver.find_element(By.ID, "email").send_keys("a@b.id") driver.find_element(By.ID, "password").send_keys("rahasia123") driver.find_element(By.CSS_SELECTOR, "button[type=submit]").click() WebDriverWait(driver, 10).until(EC.url_contains("/dashboard")) # explicit wait assert "Selamat datang" in driver.page_source

11.4

Cypress

Skenario yang sama dalam Cypress. Perhatikan tidak ada penantian eksplisit: Cypress otomatis mengulang pengecekan sampai kondisi terpenuhi atau waktu habis.

describe("Login", () => { it("berhasil dengan kredensial valid", () => { cy.visit("/login"); cy.get('[data-testid="email"]').type("a@b.id"); cy.get('[data-testid="password"]').type("rahasia123"); cy.get("button[type=submit]").click(); cy.url().should("include", "/dashboard"); cy.contains("Selamat datang").should("be.visible"); }); it("menampilkan error untuk password salah", () => { cy.visit("/login"); cy.get('[data-testid="email"]').type("a@b.id"); cy.get('[data-testid="password"]').type("salah"); cy.get("button[type=submit]").click(); cy.get('[data-testid="error"]').should("contain", "tidak valid"); }); });
✓Selalu sertakan skenario negatif (password salah, kolom kosong), bukan hanya jalur sukses, sama seperti pada unit test.
11.5

Praktik Terbaik & Flaky Test

Flaky test adalah test yang kadang lulus dan kadang gagal pada kode yang sama. Test seperti ini merusak kepercayaan tim terhadap hasil pengujian.

Penyebab umumSolusi
Memakai sleep() dengan waktu tetapGunakan explicit wait / auto-retry berbasis kondisi
Test saling bergantung atau berbagi dataSetiap test menyiapkan dan membersihkan datanya sendiri
Locator rapuhGunakan data-testid yang stabil
Bergantung pada layanan eksternalStub/mock respons atau pakai lingkungan test khusus

Page Object Model (POM)

Pisahkan detail halaman (locator, aksi) dari logika test. Perubahan UI cukup diperbaiki di satu tempat.

class LoginPage: def __init__(self, driver): self.driver = driver def login(self, email, password): self.driver.find_element(By.ID, "email").send_keys(email) self.driver.find_element(By.ID, "password").send_keys(password) self.driver.find_element(By.CSS_SELECTOR, "button[type=submit]").click() def test_login(driver): driver.get("https://contoh.app/login") LoginPage(driver).login("a@b.id", "rahasia123") # test tetap ringkas
11.6

Otomasi Pengujian API

Untuk sistem web service seperti proyek lintas mata kuliah, pengujian otomatis pada level API lebih cepat dan stabil daripada UI. Contoh dengan requests + PyTest:

import requests BASE = "https://api.contoh.app" def test_get_produk_mengembalikan_200_dan_daftar(): r = requests.get(f"{BASE}/produk", timeout=10) assert r.status_code == 200 assert isinstance(r.json(), list) def test_endpoint_dilindungi_menolak_tanpa_token(): r = requests.get(f"{BASE}/pesanan", timeout=10) assert r.status_code == 401
💡Pada proyek, kelompok penguji dapat memakai pendekatan ini untuk eksekusi pengujian fungsional dan keamanan dasar, lalu menjalankannya berulang saat retest setelah bug diperbaiki. Spesifikasi OpenAPI dari kelompok pembangun menjadi acuan skenario. Untuk gRPC/GraphQL, tools-nya berbeda (Postman, ghz, k6), tetapi prinsip otomasinya sama.
11.7

Pengenalan CI/CD

  • CI
    Continuous Integration
    Developer sering menggabungkan kode ke repositori bersama; setiap penggabungan memicu build dan test otomatis untuk mendeteksi masalah sedini mungkin.
  • CD
    Continuous Delivery
    Kode yang lolos pipeline selalu siap dirilis; rilis ke produksi tetap lewat persetujuan manual.
  • CD
    Continuous Deployment
    Kode yang lolos seluruh test langsung dirilis ke produksi secara otomatis.

Tahapan Pipeline & Peran Test

TahapAktivitasTest yang dijalankan
1. Commit / PushPemicu pipeline–
2. BuildInstal dependensi, kompilasiLint / static analysis
3. Test cepatUnit test + coveragePyTest / JUnit
4. Test integrasiAPI & antarserviceTest API otomatis
5. Deploy ke stagingRilis ke lingkungan ujiSmoke test & E2E (Selenium/Cypress)
6. Deploy ke produksiRilis (manual/otomatis)Smoke test pasca-deploy

Contoh pipeline sederhana dengan GitHub Actions yang menjalankan PyTest dan menolak perubahan bila coverage di bawah batas:

# .github/workflows/test.yml name: CI on: push: branches: [main] pull_request: jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-python@v5 with: python-version: "3.12" - run: pip install -r requirements.txt pytest pytest-cov - run: pytest --cov=. --cov-branch --cov-fail-under=80
⚠Quality gate: pipeline harus benar-benar menggagalkan build ketika test gagal atau coverage di bawah ambang. Pipeline yang gagalnya diabaikan sama saja tidak ada. Jangan pula menaruh secret (API key, token) di dalam file workflow; gunakan fitur secrets dari platform CI.

Untuk proyek, memasang pipeline seperti ini sebelum code freeze (minggu 12) membantu kelompok pembangun menjaga sistem tetap stabil dan memudahkan retest otomatis pada minggu 14.

Latihan Kelas: Merancang Strategi Otomasi

Kerjakan berkelompok selama 15 menit.

Latihan

Otomasi untuk Sistem Proyek Anda

Gunakan topik sistem kelompok Anda (mis. reservasi tiket, marketplace).

  • Dari 8 skenario berikut, tentukan mana yang diotomasi di level unit, API, atau UI, dan mana yang dibiarkan manual: login valid, login gagal, pencarian produk, booking dua pengguna bersamaan, tampilan di layar kecil, checkout, batas rate limit, kesan estetika halaman.
  • Tulis satu skenario UI dalam format Given–When–Then, lalu ubah menjadi kerangka kode Selenium atau Cypress.
  • Gambarkan pipeline CI untuk repositori Anda: tahap apa saja dan test apa di tiap tahap.

Jika test E2E Anda gagal satu dari sepuluh kali tanpa perubahan kode, apa langkah diagnosis pertama Anda?

Rangkuman

  • ✓ Otomasi paling bernilai untuk regression, smoke test, dan test berulang; tidak semua hal layak diotomasi.
  • ✓ Selenium, Cypress, dan Playwright memiliki pendekatan berbeda; pilih sesuai kebutuhan tim.
  • ✓ Locator stabil, penantian berbasis kondisi, dan Page Object Model mengurangi flaky test.
  • ✓ Test API otomatis lebih cepat dan stabil daripada UI dan cocok untuk sistem web service.
  • ✓ CI/CD menjalankan build dan test otomatis pada setiap perubahan; quality gate menjaga mutu sebelum rilis.

Latihan Pemahaman Mandiri

Klik tiap soal untuk melihat kunci jawaban.

1. Mengapa time.sleep(5) bukan solusi yang baik untuk menunggu elemen muncul?
Jawaban: Waktu tetap bisa terlalu singkat (test gagal saat server lambat) atau terlalu lama (membuang waktu). Penantian berbasis kondisi menunggu hanya sampai elemen siap, dengan batas waktu maksimum.
2. Apa perbedaan Continuous Delivery dan Continuous Deployment?
Jawaban: Pada Continuous Delivery, kode yang lolos pipeline siap dirilis tetapi rilis ke produksi menunggu persetujuan manual. Pada Continuous Deployment, rilis ke produksi terjadi otomatis setelah semua test lulus.
3. Apa manfaat Page Object Model?
Jawaban: Memusatkan locator dan aksi halaman di satu class sehingga perubahan UI hanya perlu diperbaiki di satu tempat, dan test menjadi lebih ringkas serta mudah dibaca.
4. Mengapa test UI sebaiknya lebih sedikit daripada unit test?
Jawaban: Test UI lebih lambat, lebih rapuh terhadap perubahan tampilan, dan lebih mahal dipelihara. Logika bisnis lebih efisien diuji pada level unit dan API, sedangkan UI dibatasi pada alur kritis.

Tugas Sesi 11

Otomasi Test & Pipeline CI

Gunakan repositori GitHub (boleh dari proyek kelompok atau tugas sebelumnya). Kerjakan:

(1) Minimal 3 test otomatis level UI (Selenium/Cypress/Playwright) atau level API terhadap aplikasi nyata, termasuk 1 skenario negatif
(2) Penerapan data-testid/locator stabil dan penantian berbasis kondisi (tanpa sleep tetap)
(3) Satu workflow CI (mis. GitHub Actions) yang menjalankan test dan coverage otomatis pada setiap push
(4) Tangkapan layar pipeline yang berhasil, serta satu pipeline yang sengaja digagalkan untuk menunjukkan quality gate bekerja
