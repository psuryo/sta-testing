Unit Testing (Tools: JUnit)

Setelah memahami cara merencanakan dan mendokumentasikan pengujian, kini saatnya mengeksekusi pengujian pada level terkecil: unit. Sesi ini memperkenalkan JUnit 5 sebagai framework unit testing Java, lalu ditutup dengan pengumuman proyek lintas mata kuliah Web Service × Software Testing.

⏱ 50 menit 🎯 CPMK-3, CPMK-4 🚀 Kick-off Proyek

Tujuan Pembelajaran

Setelah mengikuti sesi ini, mahasiswa mampu:

  • ✓ Menjelaskan posisi unit testing pada test level dan manfaatnya.
  • ✓ Menulis test class JUnit 5 dengan anotasi @Test, @BeforeEach, dan @AfterEach.
  • ✓ Memakai assertion, assertThrows, dan @ParameterizedTest.
  • ✓ Menerapkan pola Arrange–Act–Assert dan prinsip FIRST.
  • ✓ Memahami skema, timeline, dan rubrik proyek lintas mata kuliah.
8.1

Konsep Unit Testing

Unit testing menguji bagian terkecil kode yang dapat diuji (method atau class) secara terisolasi, biasanya ditulis oleh developer sendiri. Pada piramida pengujian, unit test berada di dasar: jumlahnya paling banyak, berjalan paling cepat, dan paling murah untuk dipelihara.

  • 01
    Umpan balik cepat
    Bug terdeteksi dalam hitungan detik, tepat di lokasi kode yang berubah.
  • 02
    Jaring pengaman refactoring
    Perubahan kode dapat dilakukan dengan percaya diri karena regresi segera terlihat.
  • 03
    Dokumentasi hidup
    Test menunjukkan perilaku yang diharapkan dari sebuah method.
💡Hubungan dengan sesi sebelumnya: teknik EP dan BVA (sesi 5) menentukan data apa yang diuji, sedangkan Statement/Branch Coverage (sesi 6) mengukur seberapa banyak kode yang tersentuh. JUnit adalah alat untuk mengeksekusi keduanya secara otomatis.
8.2

Anatomi Test JUnit 5

Contoh class yang diuji — menghitung diskon berdasarkan total belanja:

// DiscountCalculator.java public class DiscountCalculator { public double apply(double total) { if (total < 0) throw new IllegalArgumentException("Total negatif"); if (total >= 500_000) return total * 0.90; // diskon 10% return total; } }

Test class-nya, memakai pola Arrange–Act–Assert:

import org.junit.jupiter.api.*; import static org.junit.jupiter.api.Assertions.*; class DiscountCalculatorTest { private DiscountCalculator calc; @BeforeEach void setUp() { calc = new DiscountCalculator(); } // Arrange (dijalankan sebelum tiap test) @Test @DisplayName("Total tepat 500.000 mendapat diskon 10%") void diskonDiBatasAtas() { double hasil = calc.apply(500_000); // Act assertEquals(450_000, hasil, 0.001); // Assert } @Test void tanpaDiskonDiBawahBatas() { assertEquals(499_999, calc.apply(499_999), 0.001); } }
AnotasiFungsi
@TestMenandai method sebagai test
@BeforeEach / @AfterEachDijalankan sebelum / sesudah setiap test (setup & cleanup)
@BeforeAll / @AfterAllDijalankan sekali per class (method harus static)
@DisplayNameNama test yang mudah dibaca di laporan
@DisabledMenonaktifkan test sementara
✓Perhatikan contoh di atas: nilai 500.000 dan 499.999 berasal dari Boundary Value Analysis — batas diskon dan nilai tepat di bawahnya.
8.3

Assertion & Pengujian Exception

AssertionKegunaan
assertEquals(expected, actual)Nilai aktual sama dengan yang diharapkan (urutan: expected dulu)
assertTrue / assertFalseKondisi boolean
assertNull / assertNotNullPengecekan null
assertThrows(Ex.class, ...)Kode harus melempar exception tertentu
assertAll(...)Mengelompokkan beberapa assertion, semua dilaporkan meski ada yang gagal
@Test void totalNegatifDitolak() { IllegalArgumentException ex = assertThrows( IllegalArgumentException.class, () -> calc.apply(-1)); assertEquals("Total negatif", ex.getMessage()); }
⚠Skenario negatif wajib diuji. Test yang hanya mencakup jalur sukses (happy path) memberi rasa aman palsu — sama seperti pada Test Case di sesi 7.
8.4

Parameterized Test

Satu logika test dijalankan dengan banyak data — cocok untuk hasil EP/BVA yang berupa tabel nilai.

@ParameterizedTest(name = "total {0} → {1}") @CsvSource({"0, 0", "499999, 499999", "500000, 450000", "1000000, 900000"}) void hitungDiskon(double total, double diharapkan) { assertEquals(diharapkan, calc.apply(total), 0.001); }

Dependensi Maven: org.junit.jupiter:junit-jupiter (versi 5.x) dan junit-jupiter-params untuk parameterized test. Jalankan dengan mvn test atau dari IDE.

8.5

Praktik Terbaik: Prinsip FIRST

Lakukan (FIRST)

  • Fast — cepat dieksekusi
  • Independent — tidak bergantung pada test lain atau urutan eksekusi
  • Repeatable — hasil sama di lingkungan mana pun
  • Self-validating — lulus/gagal otomatis, tanpa cek manual
  • Timely — ditulis bersamaan dengan kode

Hindari

  • Test yang memanggil database/jaringan sungguhan (gunakan mock)
  • Banyak tujuan pengujian dalam satu method test
  • Nama test seperti test1 yang tidak informatif
  • Mengejar angka coverage tanpa assertion bermakna

Latihan Kelas: Menguji Method Validasi

Kerjakan berpasangan selama 12 menit.

Latihan

Validasi Umur Pendaftar

Requirement: "Method isEligible(int umur) mengembalikan true jika umur 17–60 (inklusif), dan melempar IllegalArgumentException jika umur negatif."

  • Tentukan nilai uji dengan BVA (6 nilai batas) dan satu nilai negatif.
  • Tulis test class JUnit 5 dengan satu @ParameterizedTest dan satu assertThrows.

Jika implementasi salah menulis umur > 17 alih-alih >= 17, test mana yang akan gagal?

Rangkuman

  • ✓ Unit test menguji unit terkecil secara terisolasi dan menjadi fondasi piramida pengujian.
  • ✓ JUnit 5 menyediakan anotasi siklus hidup, assertion, dan dukungan test berparameter.
  • ✓ Pola Arrange–Act–Assert menjaga test tetap terstruktur dan mudah dibaca.
  • ✓ Data uji dari EP/BVA diterapkan langsung lewat @ParameterizedTest; jalur negatif diuji dengan assertThrows.
  • ✓ Test yang baik memenuhi prinsip FIRST.

Latihan Pemahaman Mandiri

Klik tiap soal untuk melihat kunci jawaban.

1. Apa perbedaan @BeforeEach dan @BeforeAll?
Jawaban: @BeforeEach berjalan sebelum setiap test (state segar tiap test), sedangkan @BeforeAll berjalan sekali sebelum seluruh test dalam class dan method-nya harus static.
2. Mengapa test harus independen satu sama lain?
Jawaban: Agar hasil tidak bergantung pada urutan eksekusi dan kegagalan satu test tidak menyebabkan kegagalan berantai, sehingga lokasi bug mudah ditelusuri.
3. Kapan @ParameterizedTest lebih tepat daripada beberapa @Test terpisah?
Jawaban: Ketika logika pengujian sama dan hanya data input/expected yang berbeda, seperti nilai-nilai hasil EP atau BVA. Ini mengurangi duplikasi kode.
4. Coverage 100% sudah menjamin tidak ada bug. Benar atau salah?
Jawaban: Salah. Coverage hanya mengukur kode yang dieksekusi, bukan kebenaran hasilnya. Test tanpa assertion yang bermakna tetap menaikkan coverage tanpa menemukan bug.

Proyek Lintas Mata Kuliah: Web Service × Software Testing

Kick-off hari ini. Dosen pengampu: Philipus Suryo Subandoro · Periode: Minggu 8 hingga UAS · 5 kelompok.

Ringkasan

Tiap kelompok membangun satu sistem web service sesuai topik yang ditugaskan, lalu sistem tersebut diuji secara independen oleh kelompok lain lewat rotasi silang. Hasil akhirnya adalah satu laporan gabungan per sistem (bagian pengembangan + bagian pengujian) dalam format jurnal ilmiah.

💡Mengapa digabung: mencerminkan kolaborasi dev–QA di industri; pengujian oleh pihak independen lebih objektif; laporan lebih kuat secara metodologis untuk dikembangkan menjadi draft jurnal.

Dokumentasi Wajib Saat Code Freeze (Minggu 12)

  • ✓ Spesifikasi OpenAPI lengkap untuk endpoint REST (lanjutan lab 03).
  • ✓ Skema GraphQL (dengan contoh query/mutation) atau file .proto untuk gRPC.
  • ✓ README: cara menjalankan/mengakses sistem, daftar endpoint, cara autentikasi (lanjutan lab 07).
  • ✓ Daftar environment variable untuk penguji (gunakan placeholder, jangan bocorkan secret asli).
  • ✓ URL deployment yang stabil (Render/Vercel/Cloudflare).
